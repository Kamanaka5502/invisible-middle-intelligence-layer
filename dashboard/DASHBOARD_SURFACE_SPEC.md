# Dashboard Surface Specification

## Position

The Invisible Middle dashboard is not the product.

The dashboard is the visibility surface for the intelligence architecture underneath it.

The product is the structural interpretation layer: signal intake, contextual interpretation, structural inference, hidden compensation mapping, burden/flourishing assessment, response guidance, evidence surface, and optional boundary interface.

## Dashboard Purpose

The dashboard exists to make hidden human compensation visible without reducing the layer to productivity analytics, engagement tracking, behavioural scoring, or surveillance.

It should answer:

- Where is burden transferring?
- Who is carrying it?
- Which dimension is under pressure?
- Where did authority shift?
- Where did context collapse?
- Where did repeated checking appear?
- Where is flourishing degrading?
- What must be rebalanced?

## Dashboard Must Not Become

- a productivity dashboard
- a user satisfaction dashboard
- an employee surveillance surface
- a generic AI monitoring interface
- a wellbeing-branding screen
- a behavioural blame tool
- a protected Elyria / Veritas runtime surface

## Core Views

### 1. Signal Field View

Shows observed signal families:

- behavioural signals
- workflow signals
- communication signals
- AI interaction signals
- governance signals
- temporal signals

Purpose:

> Show what is appearing without pretending the signal alone is the diagnosis.

### 2. Structural Interpretation View

Shows likely structural conditions:

- interpretive instability
- trust instability
- closure failure
- threshold ambiguity
- ownership drift
- workflow incoherence
- context fragmentation
- predictability instability
- escalation inflation
- AI burden transfer
- hidden governance weakness

Purpose:

> Show what the signal pattern may structurally mean.

### 3. Human Compensation Map

Shows who is carrying the invisible work:

- child / learner
- parent / carer
- teacher / practitioner
- caseworker
- employee
- manager
- service user
- reviewer
- human overseer

Purpose:

> Make visible who is carrying what the system failed to hold.

### 4. Burden Field View

Shows burden domains:

- cognitive burden
- interpretive burden
- verification burden
- monitoring burden
- decision burden
- authority burden
- context reconstruction burden
- closure burden
- workflow repair burden
- escalation burden
- trust repair burden
- AI oversight burden

Purpose:

> Show the type of hidden load being redistributed.

### 5. Flourishing Field View

Shows healthy containment and flourishing indicators:

- interpretive confidence
- trust stability
- closure confidence
- sustainable participation
- ownership clarity
- decision confidence
- predictability stability
- reduced monitoring dependency
- lower compensation burden
- cognitive sustainability
- healthy autonomy
- stable workflow participation

Purpose:

> Show whether the system leaves people more capable, or merely more processed.

### 6. Rebalance View

Shows response pathways:

- diagnostic response
- design response
- governance response
- human review response
- AI oversight response
- optional boundary response

Purpose:

> Convert interpretation into structural restoration guidance.

## Dashboard Finding States

Recommended public finding states:

- SMOOTH
- FRICTION
- DISPLACEMENT
- AUTHORITY SHIFT
- CONTEXT COLLAPSE
- RECHECK LOOP
- TRUST DAMAGE
- PARTICIPATION LOSS
- REBALANCE REQUIRED
- FLOURISHING SUPPORT
- UNFIT

## Design Principle

The dashboard should feel calm, serious, and human-readable.

It should not overwhelm users with raw metrics.

It should show structural meaning, evidence strength, human burden location, and rebalance direction.

## Boundary

The dashboard may show public diagnostic findings and evidence envelopes.

It must not expose protected substrate mathematics, private admissibility machinery, scoring law, kernelization logic, enforcement internals, customer law bundles, or live consequence-boundary runtime.
